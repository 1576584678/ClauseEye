## 2. 规则库：为什么是"两层包"而不是直接改旧包

MVP 的 56 条种子规则已被单测与示例文档锁定（每个示例必须命中一组固定规则 id）。V1 采用**加法式结构**：

- `rulePack.<scene>.ts`：种子包，规则 id 与判定逻辑保持不变；
- `rulePack.<scene>.v1.ts`：扩充包，只新增规则；
- `src/core/rules/index.ts` 按「种子包 → 扩充包」顺序拼接，`RULES_VERSION` 升为 `0.6.0-v1`。

好处是扩充规则时不需要动回归基线，也不会因为顺序变化让同一文档的命中集合漂移。

| 规则包 | 种子 | v1 扩充 | 合计 |
|---|---|---|---|
| labor 劳动合同 | 10 | 15 | 25 |
| rent 租房 | 10 | 15 | 25 |
| offer Offer | 9 | 13 | 22 |
| nda 保密协议 | 5 | 11 | 16 |
| service 服务协议 | 6 | 12 | 18 |
| resignation 离职证明 | 4 | 9 | 13 |
| injury 工伤鉴定 | 4 | 9 | 13 |
| house 二手房买卖 | 12 | 0 | 12 |
| decoration 装修合同 | 12 | 0 | 12 |
| driving 驾培协议 | 12 | 0 | 12 |
| common 通用 | 6 | 12 | 18 |
| **合计** | **90** | **96** | **186** |

> 去重规则：`engine.ts` 在合并结果时会剔除"通用包与场景包命中同一条款"的重复项，保留更具体的场景规则；同一规则同一条款只报一次。

## 3. 评测基准

`src/core/eval/benchmarkCases.ts` 收录 26 条用例，每条包含一段真实语境下的条款文本与两组标注：

- `expectHit`：必须命中的规则 → 用来算**召回率**（漏报）
- `expectMiss`：必须不命中的规则 → 用来算**误报**

`runBenchmark()` 输出：

| 指标 | 当前值 | 含义 |
|---|---|---|
| 召回率 | 100% | 标注要求命中的规则一条都没漏 |
| 误报 | 0 条 | 标注为"不应命中"的规则未被触发（含 5 条"合规条款不应误报"的负例） |
| 引用可定位率 | 100% | 每条风险的 `quote` 都能在原文中精确切片（防幻觉硬约束） |

用法：

```bash
npm run benchmark              # 打印报告
npx vitest run src/core/tests/benchmark.test.ts
```

基准同时纳入 CI（`npm test`），规则改动导致漏报/误报会直接让流水线失败。

**踩过的坑**：最初 5 条用例被判为「其他文档」，导致场景规则不参与匹配而"漏报"。根因是分类器按整篇文档打分，两行片段缺少场景关键词。解法是在用例里补上真实文档标题（如 `保密协议`、`劳动能力鉴定结论通知书`），这也更接近真实导入场景——顺带验证了"分类 → 规则"的联动是正确的。

## 4. 系统级到期提醒

**分工**：渲染进程算"该不该提醒"，主进程只负责"弹通知"。

- 纯函数 `src/core/reminders.ts`：
  - `collectReminders(documents)` 抽取所有带绝对日期的关键日期；
  - `daysUntil(date, now)` 按本地日历天计算；
  - `planReminders(items, { leadDays, notified })` 产出三类提醒：`advance`（提前 N 天）、`due`（当天）、`overdue`（逾期）；
  - 每个 `(文档|标签|日期|阶段)` 只提醒一次，用 `noticeKey` 去重。
- `src/desktop/reminderNotifier.ts`：文档/设置变化时立即检查一次，之后每 10 分钟检查一次（跨天也能覆盖）；去重日志存 `localStorage`（只含标题与日期，无正文）。
- 主进程 `reminders:notify` 弹 `Notification`，点击时通过 `reminders:open-document` 让渲染进程跳到对应文档详情页。
- 提醒最多打扰三次，设置页可调"提前天数"（1/3/7/14/30 天）、关闭通知、发送测试通知、重置提醒记录。
- **后台常驻（v0.5.0）**：默认关闭窗口后收进系统托盘继续运行，提醒不再依赖主窗口开着；可选开机自启（`--hidden` 静默进托盘）。偏好单独存在 `<userData>/preferences.json`——窗口关闭时渲染进程可能还没解锁保险箱，主进程必须能自己判断该不该退到托盘；托盘不可用（部分 Linux 桌面）时自动回落为"关闭即退出"并在设置页说明。

## 5. 本地 OCR

设计文档原推荐 PaddleOCR，但本机没有 MSVC 工具链（PaddleOCR 依赖 PaddlePaddle 原生库），因此改用 **tesseract.js**：纯 WASM、无需编译、可完全离线。

**离线语言包**：`scripts/fetch-tessdata.mjs` 从 `tesseract-ocr/tessdata_fast` 拉取 `chi_sim.traineddata`（2.35 MB）与 `eng.traineddata`（3.92 MB）到 `public/tessdata/`，构建时随包分发；`electron/ocr.cjs` **强制要求本地语言包存在**，找不到就直接报错，绝不回退到 CDN（否则"离线"承诺会被悄悄破坏）。

**分工**：渲染进程负责"渲染"，主进程负责"识别"。

- `src/ingest/ocr.ts`：图片用 `createImageBitmap` + canvas 缩放到最长边 2200px 后转 PNG dataURL；扫描版 PDF 用 pdfjs 逐页渲染（scale 自适应，白底填充，避免透明区域影响识别）。
- `src/ingest/ocrPlan.ts`（v0.5.0）：页数规划与"分批"边界纯函数（上限 120 页 / 每批 20 页），每批结束 `await` 一次让出主线程，界面能持续刷新百分比进度；每页识别后立即 `page.cleanup()` 释放渲染资源。
- `electron/ocr.cjs`：`tesseract.js` 的 Node Worker 常驻复用（按语言组合缓存），`asar.unpacked` 路径映射保证 WASM 能从真实文件加载；单页平均 0.5～2 秒。
- `electron/ocr.cjs` 会把 worker 脚本指向 `app.asar.unpacked`，并给引擎初始化加了 90 秒兜底超时：worker 起不来时直接返回错误提示，不会让识别无限等待（打包后的依赖解包要求见第 9 节）。
- 单次导入最多识别 120 页（超出会在 warnings 里说明并给出遗漏页数），单页图片上限 24 MB。
- 识别结果会附带置信度提示："关键数字与期限请人工复核"。

**实测**：Electron 内渲染 700×140 的"劳动合同试用期六个月 / ClauseEye OCR"图片，识别结果 96% 置信度、文字完全正确，且已作为冒烟自检的固定检查项（`npm run electron:smoke`）。

## 6. 系统钥匙串

威胁模型：无口令模式下主密钥原本明文躺在本地库里，拷走库文件即可解密全部文档。V1 用 Electron `safeStorage`（Windows DPAPI / macOS Keychain）把主密钥绑定到当前系统账号。

- 主进程：`keychain:available / save / load / clear`，密文写到 `%APPDATA%\ClauseEye\keychain.bin`（DPAPI 加密后再 base64），失败一律返回 `false` 而不是抛错。
- 渲染进程：`keychainBridge` 做能力探测；浏览器环境自动降级为不可用。
- `Vault`：
  - 创建无口令保险箱时优先写入钥匙串（`meta.keychain = true`，不再保存 `plainKey`）；
  - 解锁时优先读钥匙串，读不到才回退 `plainKey`；
  - **老库自动升级**：解锁成功后把主密钥镜像进钥匙串并写回元数据；
  - `wipe()` 同时清理钥匙串条目。
- 口令模式不受影响（主密钥由口令派生的 KEK 包裹），钥匙串开关仅对无口令模式生效。

## 7. 单文件加密库（SQLCipher 等价方案）

原定的"SQLCipher / Tauri 迁移"在动手前做了可行性评估，结论是**不引入原生 SQLCipher、不迁移 Tauri**，改为落地等价目标：

- **Tauri 不迁移**：Tauri 用系统 WebView 承载前端，IndexedDB 与 tesseract.js WASM（`SharedArrayBuffer` / Worker）在各平台行为不一致，等于重写存储层 + OCR 引擎；收益只有包体积变小，风险与工作量都不划算。
- **不引入 SQLCipher 本体**：它需要三平台预编译原生扩展（Windows 还要 MSVC），本地开发机无法编译验证，只能靠 CI 试错，迭代太慢。
- **落地做法**：保留"逐记录 AES-256-GCM 加密"，只把落盘容器从 IndexedDB 换成**单文件库**——主进程用 Electron 内置 Node 的 `node:sqlite`（`electron/vaultStore.cjs`）承载，拿到 SQLCipher 想要的三个特性：单文件、事务 + WAL 崩溃安全、可整体备份迁移，且**零原生依赖**。

实现要点：

- 表结构极简：`records(id, sealed, updated_at)` 与 `meta(key, value)`；`sealed` 存渲染进程加密后的密文 JSON，**主进程全程不接触明文与主密钥**。
- 读写原语仍是 `src/storage/db.ts`，对外 API 不变：桌面端走 `store:*` IPC，浏览器预览自动退回 IndexedDB。
- **一次性迁移**：首次切到单文件库时把旧 IndexedDB 里的记录与元数据搬过去（以 `store.migratedFromIndexedDb` 幂等标记），搬完清空旧库，避免同一份数据留两处副本。
- 设置页「数据」区块显示真实的库文件路径，方便整体备份。
- 冒烟自检新增"单文件加密库可读写"检查项（写入 → 读回 → 删除），失败即整次冒烟失败。
- 单测：`src/core/tests/vaultStore.test.ts`（容器读写 / 持久化 / 清空）与 `src/storage/db.test.ts`（驱动选择与路由）。CI 的 Node 22 默认不带 `node:sqlite`（要 `--experimental-sqlite`），该用例自动跳过；真实运行环境是 Electron 44 内置的 Node 24。

> 威胁模型与 SQLCipher 方案一致：库文件被拷走时内容仍是 AES-256-GCM 密文，密钥由口令派生的 KEK 或系统钥匙串保护。

## 8. 自动更新

三种运行形态，能力不同（`electron/updater.cjs`）：

| 形态 | 判定方式 | 更新能力 |
|---|---|---|
| installer（NSIS 安装版） | 打包后且 resources 下存在 `app-update.yml` | 完整自动更新：检查 → 下载（带进度）→ 重启安装 |
| portable（便携版 / 绿色版） | 存在 `PORTABLE_EXECUTABLE_DIR/FILE`，或缺少 `app-update.yml` | 只能"发现新版本 + 打开下载页"（便携包无法自我替换） |
| dev（未打包） | `!app.isPackaged` | 走 GitHub API 只做检查，便于验证提示链路 |

- **元数据**：安装版构建会产出 `latest.yml` 与 `*.blockmap`，应用据此判断版本与增量下载；这两个文件必须一起发布，删掉会导致自动更新失效。
- **触发时机**：应用启动 20 秒后自动检查一次（设置页可关闭"启动后自动检查"），也可随时在设置页点「检查更新」。
- **提示方式**：应用内顶部横幅（发现新版本 / 下载中百分比 / 已下载待重启）+ 系统通知；点击系统通知会打开设置页。
- **版本比较**：`compareVersions()` 是 semver 子集（忽略 v 前缀、0.10 > 0.9、预发布版比同号正式版旧），有单测覆盖。
- **隐私边界**：更新检查是应用**唯一**会主动联网的行为，且只读取 GitHub Releases 的版本号与发布说明，不上传任何本地数据；离线环境下可在设置里关闭。
- **发布即通知**：打 tag 推送后流水线自动构建并发布到 Releases；已安装用户无需任何操作——安装版下次启动检查到版本变化即提示并可一键更新，便携版 / 绿色版弹系统通知并跳转下载页。
- **签名说明**：安装包未做代码签名（无证书），Windows 可能提示"未知发布者"；功能不受影响，但升级时可能出现 SmartScreen 提醒。

## 9. 桌面交付与发布

- 打包：`electron-builder` 产出**单文件便携版 exe**（双击即运行，无需安装 Node.js/依赖）；`scripts/build-green.mjs` 额外产出绿色版目录，用于绕过 Windows 11「智能应用控制」对新签名程序的拦截。
- **绿色版的 OCR 运行时（v0.6.1 修）**：tesseract.js 在 Node 下用 `worker_threads` 跑识别，worker 的模块解析只会走真实目录、不会进入 `app.asar`。所以只把 `node_modules/tesseract.js` 解包是不够的——它自己 require 的 `is-url` / `regenerator-runtime` / `wasm-feature-detect` 少一个，就会**卡死在「创建 worker」这一步（既不报错也不返回）**，表现为冒烟自检与真实使用一起挂住。现在绿色版按 `electron/*.cjs` 的 require 反推依赖闭包（29 个包），并把整个 `node_modules` 解包到 `app.asar.unpacked`；`electron-builder` 侧对应 `asarUnpack: ["**/node_modules/**", "dist/tessdata/**/*"]`。
- **绿色版瘦身**：只保留 `zh-CN` / `en-US` 两个语言包（其余 53 个 pak 删除，省约 45 MB），`asar` 体积从约 30 MB 降到约 2.5 MB。
- 本机开发注意：工作区目录改名会 `EPERM`（文件监视器占用），`scripts/dist.mjs` 因此把 electron-builder 输出目录改到临时目录再拷回。
- CI：`ci.yml` 跑类型检查 + 单测（含评测基准）+ 前端构建；`release.yml` 在 tag 推送（或手动触发）时**并行构建 Windows / macOS / Linux** 三个平台（macOS 出 dmg + zip 双架构、Linux 出 AppImage + deb、Windows 出安装版 + 便携版 + 绿色版 zip），再由一个汇总 job 统一上传 `latest*.yml` / `*.blockmap` 并创建或更新 Release（避免多 job 争抢同一个 Release）。
- 发布流程：`git push` → 打 tag（如 `v0.6.0`）并推送 → 流水线自动产出 `ClauseEye-0.6.0-win-x64-setup.exe`、`...-portable.exe`、`ClauseEye-green-win-x64.zip`、`ClauseEye-0.6.0-mac-arm64.dmg` / `...-mac-x64.dmg`、`ClauseEye-0.6.0-linux-x86_64.AppImage`、`ClauseEye-0.6.0-linux-amd64.deb` 与 `latest*.yml` / `*.blockmap`，并写入发布说明。
- 流水线健壮性：electron-builder 只负责构建，Release 资产由 `scripts/publish-release.mjs` 直接调 GitHub REST API 上传（同名资产先删后传，失败信息可见），避免中途失败留下「只有 blockmap、没有 exe」的残缺 Release；打包失败会重试一次，仍失败则降级为仅便携版；绿色版失败只告警不阻断，且失败日志尾部会以 `::error::` 注解上报（CI 日志受限时也能定位）；CI 上 `npm ci` 后可能没有 `node_modules/electron/dist`，由 `scripts/ensure-electron-dist.mjs` 补齐后再构建绿色版；同一 tag 上残留的重复 Release 会保留资产最全的一条并删除其余；`latest` 标记指向最新版本，保证 `electron-updater` 能取到 `latest.yml`；最后一步按平台校验产物，缺平台会警告、Windows 一个 exe 都没有则整次发布判为失败。

## 10. 冒烟自检（`npm run electron:smoke`）

在无人工干预的情况下验证打包结果，检查项：

| 检查 | 说明 |
|---|---|
| 页面渲染 | `#root` 有子节点，标题栏文案正常 |
| 资源加载 | 从 `app://local` 取回 js/css 均为 200 |
| 目录穿越 | `/assets/%2e%2e/package.json` 必须被拦截（非 200） |
| 单文件加密库 | node:sqlite 容器可写入 → 读回 → 删除，且库文件位于 `userData` |
| IndexedDB | 降级路径仍可用（能建库、写对象仓库、删库） |
| 模块 Worker | pdfjs 的 ESM worker 能加载（不被 DOM 依赖绊倒） |
| preload 桥 | `window.clauseEye` 已注入，且 `shell.prefs()` 能取到托盘/自启偏好 |
| 系统能力 | 钥匙串可用、通知可用 |
| OCR 端到端 | 现场画一张中文图，交给本地引擎识别并校验文字 |
| 更新器形态 | `updater.status().mode` 必须是 installer / portable / dev 之一 |

自检窗口是隐藏的，渲染进程的定时器会被 Chromium 冻结（页面里写的超时不会触发），因此：自检会先 `setBackgroundThrottling(false)`；主进程另设 180 秒看门狗，卡死时自己写下 `FAIL` 并以非 0 退出；OCR 等关键步骤会把 `[smoke]` 前缀的分步日志转写到 stdout，直接定位卡在哪一步。

- OCR 对低分辨率、手写体、印章叠加的扫描件识别率有限；识别结果一律提示人工核对关键数字。
- 单次 OCR 上限 120 页；再长请拆分导入（识别很吃 CPU，属于有意设的上限）。
- 提醒依赖应用处于运行状态：已通过"托盘常驻 + 开机自启"解决；若用户手动关闭这两项，或系统托盘不可用，则回到"应用运行时才提醒"。
- 单文件便携版可能被 Windows 11「智能应用控制」拦截（未做代码签名），绿色版为兜底方案；后续可购买代码签名证书彻底解决。
- 存储驱动分两种：桌面端 = 单文件加密库（`<userData>/vault.sqlite`），浏览器预览 = IndexedDB。两者数据不互通；从浏览器切到桌面端时，首次启动会把旧 IndexedDB 里的记录一次性搬进单文件库。
